Missão 07

Protocolos de Segurança

Defina regras de integridade para impedir dados inválidos e proteger a consistência da base SmartCoffee.

Nível: Intermediário

Objetivo: Constraints

Checkpoint: 5 questões

Briefing

Banco confiável não depende de sorte

Uma aplicação pode errar, um formulário pode enviar valores inadequados e uma atualização pode quebrar relações. As constraints colocam regras diretamente no banco para preservar a qualidade dos dados.

01 · Conteúdo

As principais constraints

NOT NULL

Impede valores ausentes em campos obrigatórios.

nome VARCHAR(100) NOT NULL

UNIQUE

Impede repetição de valores quando a regra exige exclusividade.

email VARCHAR(150) UNIQUE

DEFAULT

Define um valor padrão quando nada é informado.

ativo BOOLEAN DEFAULT TRUE

CHECK

Valida uma condição lógica antes de aceitar o dado.

CHECK (preco > 0)

PRIMARY KEY

Identifica unicamente cada registro.

id_produto INT PRIMARY KEY

FOREIGN KEY

Conecta tabelas e protege a integridade referencial.

FOREIGN KEY (id_categoria) REFERENCES categoria(id_categoria)

02 · Demonstração

PRODUTO com regras de integridade

CREATE TABLE produto (
  id_produto INT PRIMARY KEY AUTO_INCREMENT,
  nome_produto VARCHAR(100) NOT NULL,
  descricao VARCHAR(255),
  preco DECIMAL(10,2) NOT NULL,
  estoque INT DEFAULT 0,
  id_categoria INT NOT NULL,

  CONSTRAINT chk_preco_positivo CHECK (preco > 0),
  CONSTRAINT chk_estoque_valido CHECK (estoque >= 0),
  CONSTRAINT fk_produto_categoria
    FOREIGN KEY (id_categoria)
    REFERENCES categoria(id_categoria)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
);
Regra de negócio: um produto não pode ter preço negativo, estoque negativo nem apontar para uma categoria inexistente.

03 · Laboratório

Escolha a proteção correta

Analise cada regra do SmartCoffee e escolha a constraint mais adequada.

O e-mail do cliente não pode se repetir.
O preço deve ser maior que zero.
Um novo cliente começa com status ATIVO.
Todo pedido deve estar ligado a um cliente existente.

04 · Estratégia

ON DELETE e ON UPDATE

RESTRICT

Bloqueia a exclusão quando existem registros dependentes. Útil quando apagar o registro pai geraria perda de consistência.

CASCADE

Propaga a alteração ou exclusão para registros relacionados. Deve ser usado somente quando a regra de negócio justificar.

Decisão de projeto: não existe uma opção “sempre correta”. A ação depende da regra de negócio e do risco que a operação representa.
